Este repositorio contem a resolucao da bateria de exercicios praticos da Aula 08, focada na configuracao e utilizacao do banco de dados leve e embarcado SQLite3 no ecossistema Node.js através do Query Builder Knex.js, abordando o gerenciamento de esquema via Migrations e manipulacao de dados com operacoes assincronas.

## Exercicios de Fixacao

* **EXERCICIO 01:** Adicione um método 'buscarPorId' no controller 'veiculosController.js' que consulte a tabela 'veiculos' filtrando pelo campo 'id' usando Knex (`db('veiculos').where({ id }).first()`). Caso o veículo não seja localizado, retorne HTTP Status 404.
* **EXERCICIO 02:** Adicione a rota HTTP PATCH no arquivo 'src/routes/veiculosRoutes.js' mapeando o caminho '/:id/status' para atualizar o status de um veículo diretamente na tabela SQLite via Knex.
* **EXERCICIO 03:** Crie uma nova Migration para criar a tabela 'motoristas' contendo os campos: id (primary key), nome (not nullable), cnh (unique, not nullable) e categoria (not nullable). Execute a migração via CLI.

## ## Exercício 01: Implementacao da Busca de Veiculo por ID

### ### Objetivo
Adicionar um método assíncrono chamado `buscarPorId` no controlador de veículos e mapear sua respectiva rota pública para permitir a consulta de um único registro na tabela `veiculos` do banco de dados SQLite a partir do ID enviado na URL da requisição.

### ### Código Alterado (Modificacao de src/controllers/veiculosController.js)
Atualizamos o controlador de veículos para incluir a lógica de busca por ID com validação de consistência:

```javascript
// Importa o módulo de conexão com o banco de dados configurado com Knex
const db = require('../database/connection');

const veiculosController = {
  // Os métodos anteriores (listarTodos e criar) permanecem aqui...

  // Nova função assíncrona para buscar um veículo específico pelo ID primário
  buscarPorId: async (req, res) => {
    try {
      // Captura o parâmetro dinâmico 'id' enviado na URL da requisição
      const { id } = req.params;

      // Executa a query utilizando o Knex: SELECT * FROM veiculos WHERE id = {id} LIMIT 1
      // O modificador .first() garante que o retorno seja um objeto direto e não um array
      const veiculo = await db('veiculos').where({ id }).first();

      // Se o banco de dados não encontrar nenhum registro correspondente
      if (!veiculo) {
        // Interrompe o fluxo e retorna HTTP Status 404 (Não Encontrado) com uma mensagem limpa
        return res.status(404).json({ erro: "Veículo não localizado em nossa base de dados." });
      }

      // Caso o registro exista, retorna HTTP Status 200 (Sucesso) e entrega os dados do veículo
      res.status(200).json(veiculo);
    } catch (erro) {
      // Trata erros imprevistos de comunicação com a base de dados
      res.status(500).json({ erro: "Erro interno ao consultar o banco de dados." });
    }
  }
};

module.exports = veiculosController;
```

### ### Código Alterado (Modificacao de src/routes/veiculosRoutes.js)
Mapeamos o endpoint dinâmico no arquivo de rotas para vincular o parâmetro da URL à nova função do controlador:

```javascript
const express = require('express');
const router = express.Router();
const veiculosController = require('../controllers/veiculosController');

// Rotas preexistentes do sistema
router.get('/', veiculosController.listarTodos);
router.post('/', veiculosController.criar);

// Nova Rota mapeada: O parâmetro ':id' indica um valor dinâmico passado na URL
router.get('/:id', veiculosController.buscarPorId);

module.exports = router;
```

### ### Comandos Executados para Teste
Com a aplicação em execução, disparamos consultas no terminal para checar as duas ramificações da regra de negócio:

```bash
# 1. Testando a busca por um veículo válido cadastrado (ID: 1)
curl -s http://localhost:3000/api/v1/veiculos/1 | jq .

# 2. Testando o retorno de erro 404 enviando um ID inexistente (ID: 999)
curl -s http://localhost:3000/api/v1/veiculos/999 | jq .
```

### ### Explicação Tecnica
A busca pontual por ID utiliza os recursos de parâmetros de rota nomeados do Express (`/:id`), cujos valores ficam hospedados em `req.params`. Ao repassar esse argumento para a cláusula `.where({ id })` do Knex, o Query Builder monta automaticamente uma consulta SQL sanitizada que previne falhas de segurança por injeção de código. O uso do método `.first()` altera a assinatura de retorno do banco, fazendo com que ele extraia o primeiro elemento do conjunto resultante ou devolva `undefined`, simplificando a condicional de validação na camada lógica da API.

## ## Exercício 02: Criacao da Rota HTTP PATCH para Atualizacao de Status

### ### Objetivo
Adicionar uma nova rota utilizando o método HTTP `PATCH` no arquivo `src/routes/veiculosRoutes.js` mapeando o caminho `/:id/status`. O objetivo é permitir a modificação parcial e localizada do campo `status` de um veículo específico diretamente na tabela do SQLite através do Knex.js.

### ### Código Alterado (Modificacao de src/routes/veiculosRoutes.js)
Mapeamos o novo endpoint do tipo PATCH no arquivo de rotas com comentários explicativos detalhados em cada linha:

```javascript
const express = require('express');
const router = express.Router();
const veiculosController = require('../controllers/veiculosController');

// Rotas preexistentes mapeadas no sistema
router.get('/', veiculosController.listarTodos);
router.post('/', veiculosController.criar);
router.get('/:id', veiculosController.buscarPorId);

/**
 * Nova Rota PATCH: Mapeia o caminho específico para alteração de status.
 * O ':id' captura o veículo alvo e o método aponta para a função correspondente no controller.
 */
router.patch('/:id/status', veiculosController.atualizarStatus); // Adicionado: Endpoint de atualização parcial

module.exports = router;
```

#### Atualização do Controlador (Modificacao de src/controllers/veiculosController.js)
Desenvolvemos a função assíncrona `atualizarStatus` dentro do objeto controlador para persistir a mudança no banco de dados SQLite:

```javascript
const db = require('../database/connection');

const veiculosController = {
  // ... métodos listarTodos, criar e buscarPorId mantidos ...

  // Nova função assíncrona para atualizar parcialmente o status do veículo
  atualizarStatus: async (req, res) => {
    try {
      // Captura o ID vindo dos parâmetros da URL
      const { id } = req.params;
      // Captura o novo status enviado de dentro do corpo da requisição JSON
      const { status } = req.body;

      // Validação: Garante que o campo status foi enviado na requisição
      if (!status) {
        return res.status(400).json({ erro: "O campo 'status' é obrigatório para esta atualização." });
      }

      // Executa a query SQL: UPDATE veiculos SET status = {status} WHERE id = {id}
      const atualizado = await db('veiculos').where({ id }).update({ status });

      // Se o retorno do método update for igual a 0, significa que nenhum registro foi alterado (ID inválido)
      if (!atualizado) {
        return res.status(404).json({ erro: "Não foi possível atualizar. Veículo não localizado." });
      }

      // Consulta novamente o registro atualizado para retornar ao cliente em tempo real
      const veiculoAtualizado = await db('veiculos').where({ id }).first();
      
      // Retorna HTTP Status 200 (Sucesso) entregando o objeto com o novo status persistido
      res.status(200).json(veiculoAtualizado);
    } catch (erro) {
      // Tratamento de falhas estruturais na comunicação com o banco de dados
      res.status(500).json({ erro: "Erro ao atualizar o status do veículo no banco de dados." });
    }
  }
};

module.exports = veiculosController;
```

### ### Comandos Executados para Teste
Com o servidor rodando, disparamos comandos via cURL na porta correta para validar a alteração de estado do veículo de ID 1 para "MANUTENCAO":

```bash
# 1. Executando o PATCH para modificar o status do veículo de ID 1
curl -s -X PATCH http://localhost:3005/api/v1/veiculos/1/status \
  -H "Content-Type: application/json" \
  -d '{"status":"MANUTENCAO"}' | jq .

# 2. Testando a validação de erro 404 ao tentar atualizar um ID que não existe (ID: 999)
curl -s -X PATCH http://localhost:3005/api/v1/veiculos/999/status \
  -H "Content-Type: application/json" \
  -d '{"status":"DISPONIVEL"}' | jq .
```

### ### Explicação Tecnica
O método HTTP `PATCH` é conceitualmente ideal para atualizações parciais, alterando apenas propriedades pontuais de um registro sem a necessidade de trafegar todo o objeto como exige o método `PUT`. Na camada do controlador, a instrução `.update({ status })` do Knex executa a query nativa do SQLite retornando um número inteiro que representa a quantidade de linhas afetadas; se esse valor for `0`, a API intercepta o fluxo devolvendo um código de resposta `404 Not Found`, evitando inconsistência de estados no ecossistema da aplicação.

## ## Exercício 03: Criacao da Migration para a Tabela de Motoristas

### ### Objetivo
Criar um novo arquivo de migração (Migration) via CLI do Knex para estruturar e versionar a tabela `motoristas` no banco de dados relacional SQLite, definindo os campos essenciais de identificação e suas respectivas restrições de integridade.

### ### Código Alterado (Criacao de src/database/migrations/[TIMESTAMP]_create_motoristas.js)
Desenvolvemos o arquivo de definição de esquema utilizando os métodos estruturais do Knex, adicionando comentários explicativos em cada linha:

```javascript
/**
 * Função UP: Executada automaticamente ao rodar as migrações mais recentes.
 * Cria e configura a estrutura física da tabela 'motoristas' no banco de dados.
 */
exports.up = function(knex) {
  return knex.schema.createTable('motoristas', function(table) {
    table.increments('id').primary(); // Cria uma chave primária auto-incremental numérica
    table.string('nome').notNullable(); // Campo de texto para o nome, configurado como obrigatório
    table.string('cnh').notNullable().unique(); // Código da CNH obrigatório e com restrição de valor único
    table.string('categoria').notNullable(); // Categoria da habilitação (A, B, C, D, E) obrigatória
    table.timestamp('criado_em').defaultTo(knex.fn.now()); // Registra o carimbo de data/hora atual automaticamente
  });
};

/**
 * Função DOWN: Executada exclusivamente durante operações de Rollback (reversão).
 * Remove completamente a tabela 'motoristas' do banco de dados, desfazendo a alteração.
 */
exports.down = function(knex) {
  return knex.schema.dropTable('motoristas');
};
```

### ### Comandos Executados no Terminal
Utilizamos a interface de linha de comando (CLI) para gerar o arquivo base e aplicar as modificações estruturais na nossa base SQLite:

```bash
# 1. Gerando o arquivo base de migração com o prefixo de timestamp automático
npx knex migrate:make create_motoristas

# 2. Executando a nova migration para criar a tabela fisicamente dentro do banco database.sqlite
npx knex migrate:latest
```

### ### Explicação Tecnica
O gerenciamento estrutural de tabelas através de arquivos de **Migrations** elimina a necessidade de manipulação manual via scripts SQL nativos (`CREATE TABLE`), mitigando erros humanos em ambientes de produção. O método `.notNullable()` cria uma restrição rígida no banco que impede a inserção de registros nulos, enquanto a propriedade `.unique()` aciona um índice de unicidade sobre a coluna `cnh`, impedindo o cadastro duplicado de documentos de motoristas e garantindo a consistência relacional e integridade dos dados da aplicação.

## ## Exercício 04: Controle de Versao do Esquema via CLI do Knex (Rollback e Reexecucao)

### ### Objetivo
Dominar a interface de linha de comando (CLI) do Knex.js para gerenciar o histórico de atualizações do banco de dados, executando a reversão segura do último bloco de migrações aplicado (Rollback) e realizando a reaplicação imediata para fins de auditoria e validação estrutural.

### ### Comandos Executados no Terminal
Executamos as instruções na CLI do Knex para manipular o estado das tabelas relacionais do SQLite:

```bash
# 1. Revertendo o último bloco de migrations executado (Desfaz a criação da tabela motoristas)
npx knex migrate:rollback

# 2. Reaplicando todas as migrações pendentes para reestruturar o banco de dados completamente
npx knex migrate:latest
```

### ### Exemplo de Saídas Capturadas no Console
```text
$ npx knex migrate:rollback
Batch 2 rolled back: 1 migrations

$ npx knex migrate:latest
Batch 2 run: 1 migrations
```

### ### Explicação Tecnica
Os comandos de gerenciamento de esquema da CLI do Knex controlam o histórico estrutural do banco por meio de grupos chamados *Batches* (Lotes). Quando o comando `migrate:rollback` é acionado, o Knex busca na tabela interna de controle qual foi o último lote injetado e executa a função `down` contida exclusivamente nos arquivos daquele lote, removendo a tabela física do SQLite de forma limpa. Ao rodar em seguida o `migrate:latest`, a função `up` é reexecutada, lendo o arquivo novamente. Esse ciclo é essencial para depuração durante a fase de desenvolvimento, pois permite testar se os métodos de destruição e construção do banco estão síncronos e livres de falhas relacionais.
