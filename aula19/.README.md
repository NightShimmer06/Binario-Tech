# Atividade Pratica - Aula 19: DevOps, Deploy e Automacao de Infraestrutura

Este repositorio contem a resolucao da bateria de exercicios praticos da Aula 19, focada no gerenciamento de processos Node.js utilizando PM2, persistencia de aplicacoes em background e automacao com scripts Bash.

## Exercicios

* **EXERCICIO 1:** Configure o PM2 para limitar o uso maximo de memoria do processo `api-telemetria` em 100MB utilizando a flag `--max-memory-restart 100M`.

* **EXERCICIO 2:** Crie um arquivo de ecossistema do PM2 (`ecosystem.config.js`) definindo as variaveis de ambiente de Desenvolvimento e Producao para a aplicacao da `aula19`.

* **EXERCICIO 3:** Escreva um comando em Bash que salve a lista de processos ativos do PM2 e persista a configuracao atual para reinicializacao do sistema operacional (`pm2 save`).

* **EXERCICIO 4:** Realize o commit e o push das alteracoes da `aula19` para a branch `main` do GitHub garantindo o versionamento correto no servidor.

## Exercicio 1: Limitacao de Memoria Preventiva

### Objetivo
Configurar o PM2 para monitorar o consumo de memoria RAM da aplicacao `api-telemetria`. Se o processo ultrapassar 100MB, o PM2 deve reinicia-lo automaticamente para prevenir travamentos no servidor (Memory Leaks).

### Codigo Original / Comando Anterior
No fluxo padrao da aula, a aplicacao foi iniciada sem restricoes de hardware com o comando:
```bash
pm2 start server.js --name "api-telemetria"
```

### Codigo Alterado / Novo Comando
Para aplicar a regra de corte de memoria, removemos a instancia antiga e iniciamos o processo aplicando a flag `--max-memory-restart`:
```bash
# 1. Remove a instancia antiga sem limites da tabela do PM2
pm2 delete api-telemetria

# 2. Inicia o processo aplicando a trava de seguranca de 100 Megabytes
pm2 start server.js --name "api-telemetria" --max-memory-restart 100M
```

### Explicacao Tecnica
A flag `--max-memory-restart 100M` faz com que o daemon do PM2 inspecione o PID do Node.js continuamente. Caso a aplicacao consuma mais do que 100MB devido a um loop ou sobrecarga de requisicoes, o PM2 realiza um restart limpo em milissegundos, liberando a memoria RAM sem derrubar o servico definitivamente.

## Exercicio 2: Arquivo de Ecossistema Multiambiente (ecosystem.config.js)

### Objetivo
Substituir a inicialização por comandos manuais de terminal por um arquivo de configuração centralizado. O arquivo deve gerenciar o processo e definir variáveis de ambiente distintas para os ambientes de Desenvolvimento e Produção.

### Codigo Original (server.js)
O código original lia apenas uma porta padrão ou do arquivo `.env`, sem distinção explícita de ambiente para banco de dados:
```javascript
const PORT = process.env.PORT || 3000;
```

### Codigo Alterado (Criacao do ecosystem.config.js)
O arquivo deve ser criado na raiz da pasta `aula19` com o nome `ecosystem.config.js`. A sua estrutura declarativa centraliza as flags do Exercício 1 e separa os escopos de variáveis:

```javascript
module.exports = {
  apps : [{
    name: 'aula19',                  // Nome centralizado do processo na tabela PM2
    script: './server.js',           // Aponta para o script raiz da aplicacao
    
    // Configuracoes de hardware e comportamento obtidas no Exercicio 1
    instances: 1,                    // Numero de instancias rodando
    autorestart: true,               // Reinicia automaticamente se o codigo der crash
    watch: false,                    // Desativado para evitar restarts por mudanca de logs
    max_memory_restart: '100M',      // Limitacao integrada exigida no Exercicio 1

    /* 
       VARIAVEIS DE AMBIENTE - PADRAO (DESENVOLVIMENTO)
       Ativadas executando apenas: pm2 start ecosystem.config.js
    */
    env: {
      NODE_ENV: 'development',
      DB_HOST: 'localhost',          // Banco de dados local de testes
      DB_USER: 'root',
      DB_PASS: 'dev_password_btech'
    },

    /* 
       VARIAVEIS DE AMBIENTE - PRODUCAO
       Ativadas explicitamente via flag: pm2 start ecosystem.config.js --env production
    */
    env_production: {
      NODE_ENV: 'production',
      DB_HOST: '192.168.10.50',      // IP do Servidor de Banco de Dados de Producao
      DB_USER: 'admin_prod',
      DB_PASS: 'X9#mK2!zP8qW_secure' // Senha forte de ambiente isolado
    }
  }]
};
```

### Explicacao Tecnica
O arquivo de ecossistema elimina a necessidade de decorar comandos longos no terminal. O bloco `env` mapeia o ambiente local por padrão, enquanto o bloco `env_production` substitui as credenciais em tempo de execução quando a flag `--env production` é informada. Isso garante que a aplicação não misture dados de teste com dados reais de produção.

## Exercicio 3: Criacao do Comando de Persistencia Global (save)

### Objetivo
Escrever um script em Bash que salve o estado atual dos processos ativos do PM2 para que o servidor não perca o deploy caso a máquina sofra uma reinicialização física. O comando deve ser global, funcionando de qualquer diretório do sistema através da configuração da variável PATH com o comando export.

### Codigo Original (Comando manual isolado)
O comando básico que o PM2 fornece para salvar a lista é executado de forma manual:
```bash
pm2 save
```

### Codigo Alterado (Criacao do Script Autonomo e Global)
Criamos um script executável chamado `save` (sem extensão) dentro da pasta `aula19`:
```bash
# 1. Abre o editor para criar o arquivo dentro de aula19
nano save
```

**Conteúdo do script (`aula19/save`):**
```bash
#!/bin/bash
# Script de Automacao DevOps - Binario Tech

echo "=========================================="
echo "    PERSISTINDO DAEMON DO PM2 NO SISTEMA"
echo "=========================================="

# Salva a lista de processos ativos no arquivo de dump local (~/.pm2/dump.pm2)
pm2 save

echo "--> Estado atual gravado no disco com sucesso!"
echo "=========================================="
```

Damos a permissão de execução para o arquivo:
```bash
chmod +x save
```

#### Tornando o comando Global com export
Para cumprir a exigência de rodar em qualquer diretório do terminal sem precisar mover arquivos para pastas de sistema, injetamos a pasta da atividade na variável PATH do Linux.

Para escopo imediato no terminal atual:
```bash
export PATH="$PATH:$PWD"
```

Para tornar o comando permanente (persistente mesmo após fechar o terminal), adicionamos a configuração no arquivo de perfil do usuário (`~/.bashrc`):
```bash
echo 'export PATH="$PATH:/home/caroline.sagaes/01 - curso-pbe1/Binario-Tech/aula19"' >> ~/.bashrc
source ~/.bashrc
```

### Explicacao Tecnica
O script automatiza a gravação do estado do PM2. Ao usar o comando `export PATH`, informamos ao sistema operacional que a pasta `aula19` agora faz parte dos caminhos binários padrão. Dessa forma, o terminal consegue localizar e executar o arquivo `save` a partir de qualquer pasta, transformando o script em um comando global customizado.

## Exercicio 4: Versionamento e Publicacao (Git e GitHub)

### Objetivo
Garantir o versionamento correto de todos os novos arquivos criados (`ecosystem.config.js` e `save`) e enviar as alterações estruturais com segurança para a branch `main` do repositório remoto.

### Codigo Original / Estado Anterior
Os arquivos criados nas etapas anteriores existiam apenas localmente no ambiente do servidor e constavam como não monitorados (*untracked*) pelo Git.

### Codigo Alterado / Fluxo de Trabalho do Git
Executamos a sequência de comandos abaixo a partir do terminal na pasta raiz do projeto para registrar e enviar o progresso:

```bash
# 1. Garante que estamos na raiz correta do projeto aula19
cd ~/01\ -\ curso-pbe1/Binario-Tech/aula19

# 2. Verifica o estado atual do repositorio para validar os arquivos pendentes
git status

# 3. Adiciona os arquivos criados para a area de preparacao (staging area)
git add ecosystem.config.js save

# 4. Cria um ponto de commit com uma mensagem descritiva do progresso
git commit -m "feat: adicionado ecosystem do pm2 e script bash de persistencia global"

# 5. Envia as atualizacoes locais com seguranca para a branch remota do GitHub
git push origin main
```

### Explicacao Tecnica
O versionamento do arquivo de ecossistema garante que as definições de variáveis de ambiente e limites de hardware fiquem integradas ao ciclo de vida do software. Ao subir o script de persistência `save` junto com a infraestrutura declarativa do PM2, permitimos que outros desenvolvedores da equipe reproduzam exatamente o mesmo comportamento de deploy em diferentes servidores.
