# Atividade Pratica - Aula 07: Arquitetura Modular, Separacao de Responsabilidades e Integracao

Este repositorio contem a resolucao da bateria de exercicios praticos da Aula 07, focada na refatoracao arquitetural de uma API de telemetria automotiva, aplicando a separacao estrita de responsabilidades utilizando Rotas (Endpoints), Controllers (Regras de negocio) e Middlewares de validacao estruturada no Express.

## Exercicios de Fixacao

* **EXERCICIO 01:** Crie o controller 'src/controllers/mercedesController.js' e a rota 'src/routes/mercedesRoutes.js' para gerenciar a frota de caminhoes Actros e Atego da Mercedes-Benz.
* **EXERCICIO 02:** Conecte o novo roteador da Mercedes-Benz no arquivo 'server.js' sob o caminho '/api/v1/telemetria/mercedes'.
* **EXERCICIO 03:** Crie um middleware exclusivo de validacao de Chassis/VIN em 'src/middlewares/validaVin.js' que garante que o codigo VIN enviado no POST possua exatamente 12 caracteres.
* **EXERCICIO 04:** Aplique o middleware 'validaVin' na rota POST de telemetria da Scania e teste via cURL o envio de um VIN invalido.

## ## Exercício 01: Criacao do Roteador Modular de Telemetria Mercedes-Benz

### ### Objetivo
Construir um novo arquivo de rota e um controlador isolado utilizando os padrões de arquitetura modular para gerenciar de forma independente a listagem e o cadastro de registros de telemetria da frota Mercedes-Benz (modelos Actros e Atego), separando as responsabilidades de negócio e roteamento do arquivo principal do servidor.

### ### Código Alterado (Criacao de src/controllers/mercedesController.js)
Criamos o controlador para isolar a regra de negócio e a manipulação dos dados da montadora em memória:

```javascript
// Banco de dados simulado em memória para armazenar a frota Mercedes
let telemetriaMercedes = [
    { id: 1, modelo: "Actros 2651", vin: "9BM111222333", temperatura_motor: 84, status: "OK" },
    { id: 2, modelo: "Atego 2430", vin: "9BM444555666", temperatura_motor: 90, status: "OK" }
];

const mercedesController = {
    // Função responsável por retornar todos os registros de telemetria
    listarTelemetria: (req, res) => {
        res.status(200).json({ montadora: "Mercedes-Benz", dados: telemetriaMercedes });
    },

    // Função responsável por validar e inserir um novo registro na lista
    registrarTelemetria: (req, res) => {
        const { modelo, vin, temperatura_motor } = req.body;

        // Validação de campos obrigatórios antes do cadastro
        if (!modelo || !vin) {
            return res.status(400).json({ erro: "Campos 'modelo' e 'vin' são obrigatórios." });
        }

        const novoRegistro = {
            id: telemetriaMercedes.length + 1,
            modelo,
            vin,
            temperatura_motor: temperatura_motor || 82, // Adota 82°C como padrão caso não informado
            status: temperatura_motor > 95 ? "ALERTA_AQUECIMENTO" : "OK" // Regra de negócio térmica
        };

        telemetriaMercedes.push(novoRegistro);
        res.status(201).json(novoRegistro);
    }
};

module.exports = mercedesController;
```

### ### Código Alterado (Criacao de src/routes/mercedesRoutes.js)
Criamos o roteador isolado para expor os endpoints HTTP e vinculá-los às funções do controlador desenvolvido:

```javascript
const express = require('express');
const router = express.Router();
const mercedesController = require('../controllers/mercedesController');

// GET /api/v1/telemetria/mercedes
router.get('/', mercedesController.listarTelemetria);

// POST /api/v1/telemetria/mercedes
router.post('/', mercedesController.registrarTelemetria);

module.exports = router;
```

### ### Comandos Executados para Teste
*(Nota: Estes comandos servem para documentar como validar o módulo localmente via terminal assim que o roteador for acoplado ao servidor principal no próximo exercício).*

```bash
# Testando a listagem de registros da Mercedes (GET)
curl -s http://localhost:3000/api/v1/telemetria/mercedes | jq .

# Testando a inserção de um novo caminhão com sucesso (POST)
curl -s -X POST http://localhost:3000/api/v1/telemetria/mercedes \
  -H "Content-Type: application/json" \
  -d '{"modelo":"Axor 2544","vin":"9BM999888777","temperatura_motor":88}' | jq .
```

### ### Explicação Técnico
O uso do padrão **Controller** combinado com o `express.Router()` permite desacoplar completamente as operações de entrada da aplicação. O arquivo de rotas funciona estritamente como um mapa de direcionamento de requisições (`GET` e `POST`), enquanto o arquivo de controle assume toda a responsabilidade de executar a lógica de validação de dados, manipulação de estados do array em memória e definição dos códigos de resposta HTTP adequados (`200`, `201` ou `400`), limpando e organizando a arquitetura do ecossistema.

## ## Exercício 02: Conexao do Roteador Mercedes-Benz no Servidor Central

### ### Objetivo
Vincular e acoplar o novo roteador modularizado da Mercedes-Benz ao ecossistema global do servidor principal (`server.js`), disponibilizando e isolando seus recursos sob o prefixo de rota unificado `/api/v1/telemetria/mercedes`.

### ### Código Alterado (Modificacao de server.js)
Alteramos o ponto de entrada da aplicação para importar e injetar o roteador da Mercedes-Benz no fluxo do Express com comentários detalhados:

```javascript
// Importação dos módulos base e frameworks necessários para o servidor
const express = require('express');
const cors = require('cors');

// Importação das rotas isoladas por montadora (Padrão de Arquitetura Modular)
const scaniaRoutes = require('./src/routes/scaniaRoutes');
const mercedesRoutes = require('./src/routes/mercedesRoutes'); // Adicionado: Importa o novo roteador da Mercedes

// Inicializa a instância do aplicativo Express
const app = express();
// Define a porta padrão em que a API vai escutar as requisições
const PORT = 3000;

// Configuração dos Middlewares Globais do sistema
app.use(cors()); // Libera o acesso a API para requisições de origens diferentes
app.use(express.json()); // Habilita o Express a interpretar requisições que enviam dados no formato JSON

// Middleware global de Logging (Auditoria de acessos)
app.use((req, res, next) => {
    // Imprime no console a data/hora exata, o método HTTP (GET/POST) e a URL acessada
    console.log(`[${new Date().toISOString()}] ${req.method} em ${req.url}`);
    // Chama o next() para liberar a requisição para seguir para as rotas abaixo
    next();
});

// Agrupamento e Vinculação de Rotas por Montadora (Módulos Isolados)
app.use('/api/v1/telemetria/scania', scaniaRoutes); // Rota padrão da Scania
app.use('/api/v1/telemetria/mercedes', mercedesRoutes); // Adicionado: Vincula e expõe a rota da Mercedes-Benz

// Middleware de Tratamento de Erro 404 (Caso nenhuma rota acima seja correspondida)
app.use((req, res) => {
    // Retorna o status 404 (Não Encontrado) e encerra com mensagem JSON padronizada
    res.status(404).json({ erro: "Módulo ou Rota de Telemetria não encontrada." });
});

// Inicializa o servidor HTTP fazendo-o escutar na porta configurada
app.listen(PORT, () => {
    // Imprime o aviso de ativação com sucesso no console do terminal
    console.log(`[Binário Tech] Servidor Modularizado Ativo na Porta ${PORT}`);
});
```

### ### Comandos Executados para Teste
Com o servidor principal rodando (`node server.js`), executamos os seguintes testes via CLI para auditar a integração:

```bash
# 1. Consultando a listagem inicial padrão da Mercedes-Benz
curl -s http://localhost:3000/api/v1/telemetria/mercedes | jq .

# 2. Enviando um novo caminhão Mercedes com temperatura elevada (Simulação de alerta)
curl -s -X POST http://localhost:3000/api/v1/telemetria/mercedes \
  -H "Content-Type: application/json" \
  -d '{"modelo":"Actros 2651","vin":"9BM987654321","temperatura_motor":101}' | jq .
```

### ### Exemplo de Logs Capturados no Console
```text
[2026-08-14T15:58:12.432Z] GET em /api/v1/telemetria/mercedes
[2026-08-14T15:59:05.110Z] POST em /api/v1/telemetria/mercedes
```

### ### Explicação Tecnica
A integração utiliza a capacidade de montagem modular do Express através do método `app.use()`. Ao invés de poluirmos o arquivo central declarando cada verbo HTTP explicitamente, delegamos um prefixo de rota fixo (`/api/v1/telemetria/mercedes`) para o sub-roteador exportado. Desta forma, quando uma requisição casa com esse padrão de URL, ela é automaticamente transferida para que o sub-módulo resolva as requisições internas de forma limpa e isolada, garantindo alta escalabilidade ao projeto.

## ## Exercício 03: Criacao do Middleware Exclusivo de Validacao de Chassis/VIN

### ### Objetivo
Desenvolver uma camada de segurança intermediária (Middleware) isolada em `src/middlewares/validaVin.js` para interceptar as requisições de cadastro e garantir que o código identificador VIN (Vehicle Identification Number) recebido no corpo do `POST` possua obrigatoriamente e exatamente 12 caracteres.

### ### Código Alterado (Criacao de src/middlewares/validaVin.js)
Criamos o arquivo de middleware adicionando comentários explicativos detalhados em cada instrução lógica:

```javascript
/**
 * Middleware para validação do código VIN (Chassi) do veículo.
 * Garante que nenhuma requisição inválida prossiga para os Controllers.
 */
const validaVin = (req, res, next) => {
    // Desestrutura o campo 'vin' diretamente de dentro do corpo da requisição (req.body)
    const { vin } = req.body;

    // Verifica duas condições: se o VIN não foi enviado OU se o tamanho dele é diferente de 12
    if (!vin || vin.length !== 12) {
        // Interrompe imediatamente o fluxo e retorna Status 400 (Erro do Cliente) com uma mensagem clara
        return res.status(400).json({ 
            erro: "Validação recusada. O código VIN do chassi deve possuir exatamente 12 caracteres." 
        });
    }

    // Se o VIN passou no teste de comprimento, a função next() autoriza a requisição a seguir adiante
    next();
};

// Exporta a função para que ela possa ser injetada de forma modular em qualquer rota do sistema
module.exports = validaVin;
```

### ### Comandos Executados para Teste
*(Nota: Este arquivo armazena apenas a função de validação de isolamento, os testes reais de interceptação serão documentados no Exercício 04, ao acoplá-lo em uma rota ativa).*

```bash
# Comando para verificar se o arquivo foi criado no diretório correto de middlewares

ls src/middlewares/validaVin.js
```

### ### Explicação Tecnica
Um middleware no Express atua como um filtro no ciclo de vida de uma requisição HTTP, posicionando-se entre o recebimento do estímulo na rota e a execução da lógica final no Controller. A função recebe o parâmetro `next`, que serve como um gatilho de liberação: se os dados estiverem em perfeita conformidade, o `next()` envia o fluxo adiante; caso contrário, o middleware encerra a conexão prematuramente enviando uma resposta JSON estruturada de erro, blindando a consistência dos dados do ecossistema e evitando processamento desnecessário nas camadas de negócio.

## ## Exercício 04: Aplicacao do Middleware na Rota POST de Telemetria da Scania

### ### Objetivo
Injetar de forma local e direcionada o middleware de segurança `validaVin` no método `POST` do roteador da Scania (`src/routes/scaniaRoutes.js`), garantindo a blindagem contra cadastros de telemetria com códigos de chassi que não atendam à regra estrutural de comprimento mínimo e máximo.

### ### Código Alterado (Modificacao de src/routes/scaniaRoutes.js)
Alteramos o arquivo de rotas da Scania para importar o validador e inseri-lo na cadeia de execução do método de inserção de dados:

```javascript
// Importa o framework Express para gerenciamento das rotas
const express = require('express');
// Inicializa o componente Router do Express para criar o sub-módulo de rotas
const router = express.Router();

// Importa o controller correspondente que contém as regras de negócio da Scania
const scaniaController = require('../controllers/scaniaController');

// Importa o middleware exclusivo de validação estrutural de chassi desenvolvido no Exercício 03
const validaVin = require('../middlewares/validaVin'); // Adicionado: Importação da segurança de VIN

// GET /api/v1/telemetria/scania
// Mantém o comportamento original mapeando diretamente para a função de listagem
router.get('/', scaniaController.listarTelemetria);

// POST /api/v1/telemetria/scania
// Modificado: O middleware 'validaVin' é injetado como um interceptador intermediário.
// A requisição só alcança o 'registrarTelemetria' se o código VIN possuir exatamente 12 caracteres.
router.post('/', validaVin, scaniaController.registrarTelemetria); // Modificado: Injeção do validador local

// Exporta o roteador configurado para que o servidor central consiga consumi-lo
module.exports = router;
```

### ### Comandos Executados para Teste
Com o servidor ativo no console, disparamos testes via cURL no terminal para avaliar o comportamento do filtro de segurança:

```bash
# 1. Testando envio de requisição com VIN INVÁLIDO (apenas 5 caracteres - Deve ser rejeitado)
curl -s -X POST http://localhost:3000/api/v1/telemetria/scania -H "Content-Type: application/json" -d '{"modelo":"R450","vin":"9BS12","temperatura_motor":90}' | jq .

# 2. Testando envio de requisição com VIN VÁLIDO (exatamente 12 caracteres - Deve ser aceito)
curl -s -X POST http://localhost:3000/api/v1/telemetria/scania -H "Content-Type: application/json" -d '{"modelo":"S500","vin":"9BS123456789","temperatura_motor":92}' | jq .
```

### ### Exemplo de Resposta de Erro no Console (Retorno do Teste 1)
```json
{
  "erro": "Validação recusada. O código VIN do chassi deve possuir exatamente 12 caracteres."
}
```

### ### Explicação Tecnica
Ao injetarmos o middleware `validaVin` como o segundo parâmetro da rota `router.post()`, criamos uma cadeia de responsabilidades localizada. O roteador do Express recebe a requisição e executa sequencialmente cada função declarada da esquerda para a direita. Como o middleware avalia o tamanho da string antes que qualquer processamento de negócio aconteça, a consistência estrutural dos dados de chassi é garantida sem onerar o controller, gerando um código limpo, reaproveitável e altamente manutenível.

## ## Exercício 05: Criacao do Script Bash de Automacao 'auditoria_completa.sh'

### ### Objetivo
Desenvolver um script de automação em Shell Bash (`auditoria_completa.sh`) capaz de consultar sequencialmente todas as rotas ativas de telemetria das montadoras no servidor, validando o comportamento dos endpoints e registrando as saídas brutas de forma persistente dentro de um arquivo de log chamado `auditoria.log`.

### ### Código Alterado (Criacao de auditoria_completa.sh)
Criamos o script utilitário de terminal na raiz do projeto com comentários detalhados explicativos em cada instrução Bash:

```bash
#!/bin/bash

# Define o nome do arquivo onde os resultados dos testes serão gravados
ARQUIVO_LOG="auditoria.log"

# Limpa o arquivo de log se ele já existir, para iniciar uma nova gravação limpa
> "$ARQUIVO_LOG"

echo "====================================================" | tee -a "$ARQUIVO_LOG"
echo " INICIANDO AUDITORIA COMPLETA DE TELEMETRIA" | tee -a "$ARQUIVO_LOG"
echo "====================================================" | tee -a "$ARQUIVO_LOG"

# [TESTE 1] Consulta a rota padrão da Scania (GET)
echo -e "\n[1] Consultando Endpoints Scania (GET)..." | tee -a "$ARQUIVO_LOG"
curl -s http://localhost:3000/api/v1/telemetria/scania >> "$ARQUIVO_LOG"
echo -e "\n" >> "$ARQUIVO_LOG"

# [TESTE 2] Consulta a nova rota configurada da Mercedes-Benz (GET)
echo -e "[2] Consultando Endpoints Mercedes-Benz (GET)..." | tee -a "$ARQUIVO_LOG"
curl -s http://localhost:3000/api/v1/telemetria/mercedes >> "$ARQUIVO_LOG"
echo -e "\n" >> "$ARQUIVO_LOG"

# [TESTE 3] Envia um chassi válido para a Scania para checar integridade (POST)
echo -e "[3] Inserindo Telemetria Scania com Sucesso (POST)..." | tee -a "$ARQUIVO_LOG"
curl -s -X POST http://localhost:3000/api/v1/telemetria/scania \
  -H "Content-Type: application/json" \
  -d '{"modelo":"G410","vin":"9BS111222333","temperatura_motor":89}' >> "$ARQUIVO_LOG"
echo -e "\n" >> "$ARQUIVO_LOG"

# [TESTE 4] Força um erro de VIN inválido para auditar o funcionamento do Middleware
echo -e "[4] Testando Bloqueio de VIN Invalido no Middleware (POST Scania)..." | tee -a "$ARQUIVO_LOG"
curl -s -X POST http://localhost:3000/api/v1/telemetria/scania \
  -H "Content-Type: application/json" \
  -d '{"modelo":"R500","vin":"CHASSI_CURTO","temperatura_motor":90}' >> "$ARQUIVO_LOG"
echo -e "\n" >> "$ARQUIVO_LOG"

echo "====================================================" | tee -a "$ARQUIVO_LOG"
echo " AUDITORIA CONCLUÍDA! RESULTADOS SALVOS EM $ARQUIVO_LOG" | tee -a "$ARQUIVO_LOG"
echo "====================================================" | tee -a "$ARQUIVO_LOG"
```

### ### Comandos Executados para Teste
No terminal do Google Cloud Shell, rodamos as seguintes instruções para conceder permissão de execução e disparar a automação:

```bash
# Concede permissão de execução para o arquivo do script script
chmod +x auditoria_completa.sh

# Executa o script de auditoria em lote
./auditoria_completa.sh

# Verifica o conteúdo gerado dentro do arquivo de log utilizando o jq ou cat
cat auditoria.log
```

### ### Explicação Tecnica
O desenvolvimento de scripts Bash para testes automatizados atua como uma ferramenta de **Integração Contínua (CI)** simplificada diretamente na CLI. O operador `>>` redireciona o fluxo de saída do comando `curl` (que consome a API) anexando os dados no arquivo `auditoria.log`, enquanto o comando `tee -a` duplica a saída, mostrando o progresso em tempo real no console e salvando simultaneamente no log. Isso garante que qualquer alteração futura na arquitetura possa ser auditada instantaneamente em lote.
